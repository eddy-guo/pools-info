# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Read `STATUS.md` first for the current state, then `docs/SPEC.md`, `docs/PRIMER.md` and `docs/BRIEF.md`; the handoff traps in `docs/SPEC.md` section 7 corrupt data when skipped.
- Validation is `pnpm check` (lint, typecheck, unit tests, web build), `pnpm test:db` against a dedicated test Postgres in `TEST_DATABASE_URL` (never production, never port 5432 by habit; run it on Postgres 17 and 18 because CI is 17 and Railway is 18), and `pnpm test:e2e`. Database suites must report zero skips. `pnpm test:db` runs its integration files concurrently (Node's default is one fewer than the CPU count: three files at once on the public repository's 4-vCPU CI runner, where a read near the reader's 3 s statement budget times out under the other files' load) and ends with serial phases, one node invocation per file: `apps/api/src/broad-explore.scale.test.ts`, whose printed `52k catalog serving` and `52k creators serving` lines in the CI log are the serving-latency numbers that count, `apps/api/src/observed-market.scale.test.ts`, which bounds the raw-copy market read at 21k swaps, `apps/api/src/observed-market-rollups.scale.test.ts`, which bounds the rollup-served pool page at 80k swaps and asserts its fold never spills, and `apps/api/src/observed-market.integration.test.ts`, which reads the 21k fixture through the API and is kept out of the concurrent glob by Node's own quoted `!(observed-market)` pattern. CI's Postgres has JIT and local Homebrew Postgres has not, so never add a `--test-concurrency` flag and keep latency-asserting tests and reads near the budget in those phases (see `docs/BROAD-MARKET-SERVING.md`). The market browser suite is `pnpm test:e2e:market` (needs `TEST_DATABASE_URL`; its ports derive from the base port, pinned with `PLAYWRIGHT_MARKET_PORT` and `MARKET_API_PORT`). `pnpm test:e2e` derives its web server port per copy of the repo (`webServerPort` in `playwright.config.ts`, announced on each run, overridable with `PLAYWRIGHT_WEB_PORT`) and reuses a server already on it, which is your own worktree's: restart it after rebuilding or the suite silently grades the previous build. `pnpm test:e2e -- <files>` does not filter: this pnpm forwards a literal `--` ahead of the args into `playwright test`, so it runs the whole suite; scope a run with `pnpm exec playwright test <files>` instead. A stale `apps/web/.next` makes `pnpm typecheck` fail on a page that no longer exists, because it runs before the build that regenerates `.next/types`.
- To check a page against the production read API, start a second built server with `INDEXER_API_URL=https://api-production-9f93.up.railway.app CHAIN_REFRESH_DISABLED=0 pnpm --filter @pools/web start --hostname 127.0.0.1 --port <port>` and point one spec at it with `PLAYWRIGHT_WEB_PORT=<port> npx playwright test <spec> --workers=1`: the read API's 240 reads per minute budget is global, so parallel workers trip it and the proxy then serves preloaded pages in place of production ones.
- The screener (`apps/web/src/components/product-explore.tsx` over `apps/web/src/lib/use-explore-rows.ts`) shows the rows its URL's `limit` names, 25 by default, under the shared Show more foot in `product-common.tsx`: the hook reads from the top as far as that count reaches, at most 100 rows per request, appends each Show more's rows to the ones on hand, and drops the previous query's rows on a view, sort, window or filter change (which also drops `limit`), so the list swaps straight to skeleton rows (`data-row="skeleton"`, the existing `[data-pending="true"]` shimmer) rather than the shared `data-stale-rows` dimming that `product-wallet.tsx` still uses on plain `useProduct`, while a same-query refresh (a `generation` bump) keeps showing the rows it already has. The reserved row area is sized from the URL before any data, so a Show more clamps the count it asks for to the total it already knows rather than leaving blank rows past the list's end, and it never brings the panel's head back the way a query change does; `<html data-scroll-behavior="smooth">` in the root layout is what lets the Next router jump instead of animating on a route change.
- Following (`apps/web/src/components/following.tsx`, key `poolsinfo.following.v1`, up to 200 addresses) is the same browser-local pattern as the watchlist (`state.tsx`'s `useWatchlist`) and the my-wallet store (`my-wallet.tsx`, key `poolsinfo.my-wallet.v1`, the one address the wallet page's "This is my wallet" action marks, read by the leaderboard's YOU row and the portfolio framing): `useFollowing()` is the shared store, `FollowRowButton` the row-level toggle. The traders leaderboard (`product-traders.tsx`) reuses its row renderers for both the ranked list and the `view=following` tab, whose data comes from `apps/web/src/lib/use-followed-leaderboard.ts` (one `wallets/:address` read per followed wallet, bounded concurrency, settles once), and grows past its first page with the same `ShowMore` control as the ranked list (see the "Growable lists" entry below), never the old pagination. `.leaderboard-panel .desktop-traders`/`.mobile-traders` reserve a fixed 25-row height for the ranked list's CLS budget; a view with fewer rows (the Following tab) must add the `following-traders` class to opt out of that reservation or it renders a tall empty gap.
- The read API's JSON types are a contract with the website's response validators in `apps/web/src/lib` (`pool-response.ts`, `live-feed.ts`, `following-response.ts`, `trade-share-response.ts`, `wallet-history-response.ts`): node-postgres returns bigint columns as strings, so block heights and on-chain timestamps must be converted with `Number(...)` while exact wei and raw token amounts stay strings (`apps/api/README.md` "HTTP contract"). API integration tests import those validators directly; keep it that way so the boundary cannot drift silently.
- Layout stability is a product bar, gated by `tests/e2e/layout-stability.spec.ts` at CLS 0; the assertion itself tolerates a cumulative score under 0.001 as measurement noise (a sub-pixel of movement at 390px), so a runner-load flake reporting e.g. 0.0001277 is not a real shift, but anything at or above 0.001 still fails. That suite runs with `CHAIN_REFRESH_DISABLED=1`, so any text a second request writes stays at its first-paint value unless the spec serves that route itself; text that rewraps inside a height-reserved box still shifts. A reserved slot is therefore sized at first paint and never resized by a response: what a page can know before painting decides the height, which is why the pool page carries its screener row in `apps/web/src/lib/pool-row-memory.ts`. The shift observer only counts nodes inside the viewport (the mobile project is a Pixel 7, 412x839), so a reserved slot below the fold can resolve to a different height and still pass; when you change what sits above one, compare its pending and resolved rects directly (`tests/e2e/leaderboard-labels.spec.ts` shows the pattern). `DESIGN-DELTA.md` records how the reserved slots are sized. React rewrites a cell's plain string or number child in place, and Chrome scores rewritten text whose start moves (any right-aligned cell) as a shift, so a value that replaces a placeholder is wrapped in a fragment or element (the Launches cell in `apps/web/src/components/creators.tsx`); a right-aligned box whose width follows its text moves the same way, so it sits in a fixed track (the wallet's behaviour values). Browser-local state (`following.tsx`, `state.tsx`'s watchlist, `my-wallet.tsx`) reads localStorage through `useSyncExternalStore` with a null server snapshot, so the server paints the unset state and hydration swaps it: whatever it changes is keyed to remount as new nodes, which Chrome never scores, and keeps the width it painted (the "This is my wallet" button holds one label in both states). `/` is prerendered static, so a sorted or `?view=new` URL hydrates over the default head: a right-aligned head whose box changes with the order moves too, which is why the screener's sort arrow sits before its label and out of the flow (`.sort-arrow` in `apps/web/src/app/globals.css`). A creator's own page (`/creators/<address>/`) reserves nothing for its launches table, so it still fails this bar for any creator with more than about one matching launch in the covered catalog (only a single- or zero-launch address is exercised in `layout-stability.spec.ts`'s `creator-detail` case); closing that needs the same shown-count-plus-reserved-height pattern the leaderboards use (`apps/web/src/components/product-common.tsx`'s `ShowMore`), not yet applied to `CreatorProfile` in `creators.tsx`. A label whose eventual text is one of a few known strings but is unknown at first paint (the header strip's Live/Paused dot, `shell.tsx`'s `.subnav-live-label`) reserves the widest candidate's exact width with a `display: grid` cell and a `::before { content: "<widest string>" }` ghost at `grid-area: 1 / 1; visibility: hidden`, not a `ch`-based guess: generated content never enters `textContent`, so it never leaks into the accessible name or a `toHaveText` assertion, and the reservation is measured by the browser instead of approximated. A `display: flex`/`inline-flex` element drops the whitespace between a bare text run and a following inline child as an edge-collapse (the wallet header's address/last-trade line hit this: `.wallet-last-meta` in `globals.css` stays `display: inline`, a flex item is blockified regardless); a fact that mounts only once a read resolves needs its own fixed-width flex slot from first paint too, or the sibling that shrinks to fit beside it (an ellipsised address) reflows when the fact arrives, which the shift observer scores even though nothing looks different (`.wallet-last-meta-slot`). A `<colgroup>` fixes a `table-layout: fixed` column at first paint against re-renders that don't change data; give it whole pixels, not a `%` width, since a fractional percentage of the panel's own width can round to a different sub-pixel value between layout passes and score as a shift with byte-identical rects in the observer's own before/after log (`apps/web/src/components/product-wallet.tsx`'s positions table).
- A pool page's market (`apps/api/src/observed-market-read.ts`) has two paths that must answer identically: a cut on the canonical broad stream that the projections cover is served from `broad_market_summaries` and `broad_market_buckets` (bounded by the pool's buckets, with candle extremes from migration 018's `min_sqrt`/`max_sqrt`), and a deep-selected cut or a projection gap aggregates the raw copies per request, which is linear in the pool's swaps and was the 503 at 82k swaps. `observed-market-rollups.integration.test.ts` deep-compares the two; keep it that way when either changes (`docs/BROAD-MARKET-SERVING.md`, "Pool page from the rollups").
- Chain evidence is content-hashed per batch and replayed before commit; new sources add an evidence variant beside the existing ones (see `packages/db/src/broad.ts` and `packages/chain/src/hypersync-broad.ts`) rather than restructuring a serializer or a stream.
- The tier-2 swap history stream is `swaps:broad:v1`; its HyperSync backfill is a manual, off-by-default command documented in `docs/HYPERSYNC-BACKFILL.md` with recorded fixtures under `packages/chain/src/fixtures/hypersync/`. Key names live in `.env.example`; never print a key value.
- The live worker's chain source is `RECENT_SOURCE` (`rpc` default, `hypersync` removes its per-swap Alchemy receipts and headers and fills restart gaps from HyperSync at 30 requests per minute); design, evidence fields, residual Alchemy calls and rollout are in `docs/HYPERSYNC-TIP.md`.
- On-demand wallet history (`/v1/wallets/:address/history`) is explorer data from the Blockscout PRO API, served for display only and never joined to accounting or PnL; the key, cap, TTL variables and the per-process credit budget are documented in `apps/api/README.md`. It is the one product route the website's proxy may not answer from the preloaded dataset: `readWalletHistory` in `apps/web/src/lib/product-server.ts` passes the 503 reason and `Retry-After` through to the browser, because an invented empty history would read as a real one.
- The indexer's Alchemy cost at the tip is per registered swap (one receipt plus a shared header, about 34 CU); at the 16 Sep 2026 volume of about 30,000 registered swaps per hour the live feed alone burns about 1.0M CU per hour with the deep tier off, so the 208,000 CU per hour resume target is not reachable on Alchemy. The indexer is stopped with its source disconnected; the measurement and the resume and stop commands are in `docs/PHASE-A-RUN.md` under "Resume measurement".
- The aggregate ledger (`docs/AGGREGATE-LEDGER.md`) is being built in phases; phase 1 is the pure fold in `packages/core/src/ledger.ts`, migration 017 and the writer in `packages/db/src/ledger.ts`, nothing reads it yet. Its dump replay `packages/db/src/ledger-replay.test.ts` reads the restored production dump `pools_prod_shape` on the Postgres 18 test server (port 5418) and is the one database test allowed to skip, only where that dump is unreachable (CI); locally it must run.
- A fake-upstream test for a fetch built on `AbortSignal.timeout()` must not race a bare pending `Promise` with only an abort listener: that timer is unref'd, so Node's test runner can cancel the test as "Promise resolution is still pending but the event loop has already resolved" once nothing else keeps the loop alive (it passes alone and only fails alongside other test files, so it can look like unrelated flakiness). Point the fetch at a real, never-responding local server instead, as `apps/api/src/eth-price.test.ts` and the `deadline()` helper in `packages/token-image/src/index.test.ts` do.
- Never reset or mutate the `discovery:v1` cursor, never run collection against Alchemy or HyperSync without the captain's word, and keep `transaction_sender` labelled as an initiator, not a beneficiary.
- Growable lists (the trader leaderboard, the creators leaderboard and the screener) share one "Show more" control, `ShowMore` in `apps/web/src/components/product-common.tsx`: a `total: number | null` prop, not `number` - pass `null` until the first response names a real count, so the button reserves its space from first paint instead of popping in once the count resolves (that pop-in is a real CLS hit, not just a cosmetic one); the `.pagination` rule in `globals.css` holds the button's row in `min-height` at both widths, so the button's going once every row is on show (which a short list's first response decides) moves nothing under the list either. `product-traders.tsx`'s `useLeaderboard` and `creators.tsx`'s `useCreatorsBoard` show the append pattern: grow by fetching only `offset = rows already held`, never re-fetching a page already shown; a window or sort change is a new fetch key and resets the list from scratch, moving focus to the first newly revealed row's link once it resolves. Both leaderboards cap at 100 client-side regardless of what the read API allows, matching the read API's own top-100 leaderboard cap (`apps/api/README.md` "Creators aggregate" and "Leaderboard"); read the display total off `Math.min(total, cap)` rather than the raw API total, since a cap can land on one side before the other. The preloaded e2e fixture's leaderboard total is 52 for every window/metric combination, so a spec that wants to exercise a control's cap (e.g. the 100-row ceiling) needs to intercept the response and inflate `total`, as `tests/e2e/traders-header.spec.ts` and `tests/e2e/creators.spec.ts` do.
- The PnL share card (`apps/web/src/app/cards/[filename]/route.tsx`) has two designs picked by `card-options.ts`'s `design` field (`liquid` the default so an existing card URL's PNG stays byte-for-byte unchanged, `export` the captain's own export layout); adding a design means a new sibling branch in the route's `ImageResponse` ternary, never editing the existing branch's JSX. A satori layout with a large font (the export design's 207 px PnL) must not size its gaps with fixed `marginTop` values - the line-box can run taller than the nominal font size and a real wallet's longer figures silently push the next row off the 630 px canvas; lay the sections out with `justifyContent: "space-between"` down a flex column instead, so leftover space (not a guessed margin) absorbs the gap. The export design's profile URL sits on its own row under the ROI/Record/Best trade trio rather than beside it, because a real `poolsinfo.com/wallet/0x1234…5678` (unlike the export mockup's shortened fictional path) is long enough to collide with the trio at the card's width. A localStorage-backed toggle in a client component (the modal's design toggle) must read through `useSyncExternalStore`, matching `useFollowing`'s pattern, not `useState` plus a `useEffect` that calls `setState`: this repo's eslint config errors on `react-hooks/set-state-in-effect`, so `pnpm check` fails on the plain-effect version.
- Every wei figure renders through `Money`/`Price` (`apps/web/src/components/ui.tsx`) or `Eth` (`live-ui.tsx`); all three read the ETH/USD unit preference (`useUnit` in `state.tsx`, persisted in `localStorage` like the watchlist) and the live rate (`useEthPrice` in `eth-price-provider.tsx`, wrapping the app in `layout.tsx`) and convert with `@pools/core`'s `formatMoney` when USD is selected and the rate has resolved - a new wei display should go through one of these rather than formatting ad hoc, or it silently stays ETH-only. `Price`'s USD branch keeps the same leading-zero notation as its ETH branch for sub-cent values (most of the catalog), and `Chart`'s y-axis scales with the same rate its readout uses (the pool page's own candlestick chart, `candles.tsx`, does not yet). `GET /v1/prices/eth-usd` is proxied like wallet history: on demand, no preloaded fallback, its 503 passes through unchanged (`readEthPrice`/`EthPriceUnavailableError` in `product-server.ts`). Every fetch to `/api/product/*`, including this one, needs its own trailing slash (`next.config.ts`'s `trailingSlash: true`) or `tests/e2e/api-redirects.spec.ts` catches the 308.
- `/api/live-trades/` is polled by `TradeStream` (`trade-stream.tsx`) wherever it's rendered (`/`, a pool page) and, nowhere else, by the header strip's Live/Paused dot (`shell.tsx`) through the shared store `apps/web/src/lib/live-feed-state.ts`: `TradeStream` registers as the page's source and reports its own already-polled state; the strip reads that instead of polling a second time, and only self-polls on a page with no `TradeStream` mounted. A new global UI element that mirrors a per-page poll's state must read it the same way rather than starting an independent poll of the same endpoint, or `tests/e2e/chain.spec.ts`'s exact-call-count assertions under a faked clock (`no overlapping polls`, etc.) catch the duplicate even though a scoped run of the new element's own spec stays green.
